# Server reference

The server surface is Node-only and project-owned. It provides a framework-
neutral Web `Request`/`Response` server, a Supabase-shaped admin transport,
Express and Next.js adapters, and service/repository composition points.

## `createAuthServer`

```ts compile
import { createAuthServer, type CreateAuthServerOptions } from "mrjim-auth/server";

// Build this object with the project's PostgreSQL adapter, mailer, keys, and
// redirect policy. `createAuthServer` validates and snapshots it synchronously.
declare const options: CreateAuthServerOptions;

async function example(): Promise<void> {
  const server = createAuthServer(options);
  const response = await server.handle(
    new Request("https://example.test/auth/v1/user", {
      headers: {
        apikey: "publishable-project-key",
        authorization: "Bearer access-token",
      },
    }),
  );
  console.log(response.status);
}

void example();
```

`CreateAuthServerOptions` is `AuthServerOptions` plus an optional `services`
override. The validated server configuration contains:

| Field | Required behavior |
| --- | --- |
| `environment` | `"development"`, `"test"`, or `"production"`; defaults to production. |
| `baseUrl` | Absolute HTTP(S) URL and exact issuer origin/path. Production requires HTTPS. |
| `siteUrl` | Absolute project site URL; production requires HTTPS. |
| `database` | Complete `AuthRepository`, normally from `createPostgresAdapter`. |
| `signingKeys` | `issuer`, `audience`, `activeKeyId`, and at least one key; active material must be configured. |
| `secrets` | `tokenHashKey` and `encryptionKey`, each at least 32 decoded bytes. |
| `email` | Project-owned `Mailer` with `send(message)`. |
| `rateLimiter` | Optional `RateLimiter`; use a durable implementation for multiple instances. |
| `oauth` | Optional `google` and/or generic `oidc` client credentials. |
| `redirects.allowed` | One or more exact HTTP(S) callback URLs; no wildcard or fragment. |
| `authorization` | Optional default/protected role keys and wildcard policy. |
| `accessTokenTtlSeconds` | Integer from 300 to 3,600; default 900. |
| `refreshTokenTtlSeconds` | Integer from 3,600 to 90 days; default 30 days. |

Construction does not run migrations. Apply and verify the database schema
before accepting traffic.

## `AuthServer`

`AuthServer.handle(request)` accepts one standard Web `Request` and returns a
standard Web `Response`. The base path is normally `/auth/v1`. The server
enforces request origin policy, API-key kind, bearer authentication, route
schemas, redirect allowlists, rate limits, and current authorization context.
`AuthServer.authorize(request, requirement)` is the server-side authorization
boundary for a custom backend route and returns an `AuthSubject` when the
requirement is satisfied.

Public HTTP responses use the same envelope as the client:

```json
{ "data": { "user": null, "session": null }, "error": null }
```

or:

```json
{
  "data": null,
  "error": {
    "name": "AuthError",
    "code": "invalid_credentials",
    "message": "Invalid login credentials",
    "status": 401
  }
}
```

The OpenAPI document generated by `generateOpenApiDocument()` is the
authoritative route inventory. The public routes include signup, password and
refresh-token grants, OTP, recovery, OAuth provider discovery/authorization/
callback/exchange, current-user operations, permissions, logout, and JWKS.

## Framework adapters

### Express

```ts
import { toExpressHandler } from "mrjim-auth/express";
import type { AuthServer } from "mrjim-auth/server";

declare const server: AuthServer;
const handler = toExpressHandler(server);
void handler;
```

`toExpressHandler` translates an Express-like request into a Web `Request`,
preserves the request target, streams the Web response, and preserves multiple
`Set-Cookie` values. Configure `trustProxy: { hops }` only for a known proxy
topology; forwarded host/protocol/IP values are ignored by default.

### Next.js request client

The `mrjim-auth/nextjs/server` entrypoint exports `createServerClient`. It
requires a request-local `CookieAdapter`, optionally accepts request headers,
and creates a cookie-backed client with browser refresh/URL detection disabled.
The cookie-backed `getSession()` result is advisory. Call `getUser()` before a
server component, route handler, or action trusts identity for authorization.

## `createAdminClient`

`createAdminClient(authUrl, secretKey, options?)` is Node-only. It captures the
secret and sends it only as the `apikey` header. It deliberately does not add a
`Bearer` header. Never call it from browser code, expose the secret to a user,
or place it in a cookie.

```ts compile
import { createAdminClient } from "mrjim-auth/server";

const admin = createAdminClient(
  "https://example.test/auth/v1",
  process.env.AUTH_SECRET_KEY!,
);

async function example(): Promise<void> {
  const result = await admin.auth.admin.listUsers({ page: 1, perPage: 25 });
  if (result.error === null) console.log(result.data);
}

void example();
```

`AdminClientOptions` has only `global.fetch` and non-browser `global.headers`.
The admin namespace is immutable and each method returns
`Promise<AuthResult<unknown>>`; the server response remains under `data` and
expected failures under `error`.

### Admin namespace: 21 methods

| Method | HTTP operation | Notes |
| --- | --- | --- |
| `listUsers` | `GET /admin/users` | Page options default to `page: 1`, `perPage: 50`; each is 1–100. |
| `getUserById` | `GET /admin/users/{id}` | Returns `{ user }` or a safe error. |
| `findUser` | `GET /admin/users/find?email=...` | Exact normalized-email lookup; callers must handle `user: null`. |
| `createUser` | `POST /admin/users` | Sends the validated user-creation object. |
| `importUser` | `POST /admin/users/import` | Import-only stable UUID operation; requires a non-interactive secret API key with the exact `auth.users.import` scope and accepts only bounded profile/auth metadata. Detectable credential/session material is rejected; callers must not send secrets or sessions. |
| `updateUserById` | `PATCH /admin/users/{id}` | Sends the validated update patch. |
| `deleteUser` | `DELETE /admin/users/{id}?soft=true` | Only soft deletion is supported; `soft: false` throws/returns invalid request. |
| `inviteUserByEmail` | `POST /admin/users/invite` | Body is `{ email, options? }`; options are nested and project-defined. |
| `listRoles` | `GET /admin/roles` | Returns `{ roles }`. |
| `createRole` | `POST /admin/roles` | Role key/name/description/rank/system fields. |
| `updateRole` | `PATCH /admin/roles/{id}` | Partial role patch; system-role policy applies. |
| `deleteRole` | `DELETE /admin/roles/{id}` | Protected/system-role policy applies. |
| `setRolePermissions` | `PUT /admin/roles/{id}/permissions` | Replaces with `{ permission_ids }`. |
| `setRoleInheritance` | `PUT /admin/roles/{id}/inheritance` | Replaces with `{ inherited_role_ids }`; cycles are rejected. |
| `assignRole` | `PUT /admin/users/{id}/roles/{roleId}` | Optional `AdminScope { type, id }` becomes query parameters. |
| `unassignRole` | `DELETE /admin/users/{id}/roles/{roleId}` | Removes the global or matching scoped assignment. |
| `listPermissions` | `GET /admin/permissions` | Returns `{ permissions }`. |
| `createPermission` | `POST /admin/permissions` | Permission key is `resource.action`; dotted resources are supported. |
| `updatePermission` | `PATCH /admin/permissions/{id}` | Partial permission patch. |
| `deletePermission` | `DELETE /admin/permissions/{id}` | Role lock and permission policy apply. |
| `listAudit` | `GET /admin/audit` | Returns paged immutable audit events. |

Administrative operations are checked against dynamic permissions such as
`auth.users.manage`, `auth.roles.manage`, `auth.permissions.manage`, and
`auth.audit.read`, with project role/rank policy enforced by the server. Stable
UUID import is deliberately separate: only a non-interactive secret API-key
principal carrying the exact `auth.users.import` scope may use it; interactive
admins and wildcard/ordinary user-management scopes are rejected. Equivalent
same-UUID retries return the existing row, while UUID/email/phone conflicts fail
without overwriting. Import metadata is bounded to 8 nested levels, 100 keys
per object or array, 4,096 characters per string, and 16 KiB of serialized
JSON per metadata object. Equivalence compares the normalized email, trimmed
phone, persisted confirmation/last-sign-in/ban timestamps, metadata, and
non-deleted state; `created_at` and `updated_at` are intentionally ignored.
Omitted optional fields compare as their persistence defaults (`null` or `{}`).
The shared validator rejects detectable passwords, password hashes, sessions,
refresh/access tokens, OAuth/client secrets, private keys, credential-bearing
URLs, and other sensitive key/value patterns at every metadata depth. It is a
conservative detector rather than a proof about arbitrary opaque strings;
callers must never use import metadata for secrets, passwords, sessions, or
tokens. The server writes redacted success and failure audit records for the
import operation and rate limits administrative writes when a limiter is
configured. Service-level failures retain actor-key or actor-user correlation;
HTTP requests rejected before a valid principal exists can carry only a
request-id audit correlation, while an interactive bearer rejection is
correlated to its presenting API key rather than treated as an admin user.

## Direct service and authorization APIs

The `mrjim-auth/server` subpath also exports the token, session, user,
password, one-time-token, OAuth/OIDC, authorization, audit, API-key, rate-limit,
OpenAPI, and admin service types. These are composition APIs for trusted Node
code; they are not a browser SDK. A custom route should use
`AuthServer.authorize()` or the project's own verified subject boundary rather
than trusting client-provided role or permission data.

## Hosting and dependencies

No paid or hosted application is mandatory. The server runs in the project's
Node deployment, uses its own PostgreSQL database and mailer, and can use the
free/self-hostable adapters in this package. Express, Next.js, PostgreSQL, and
an email delivery implementation are project choices rather than hidden hosted
requirements.
